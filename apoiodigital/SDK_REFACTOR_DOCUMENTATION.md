# SDK Refactoring Documentation: New EDR Mapping

This document outlines the refactoring of the current ApoioDigital backend project into an SDK, specifically adapting the domain model to the new Entity-Relationship Diagram (EDR).

## Overview
The goal of this refactor is to transition the project from a standalone API (with controllers, direct authentication, etc.) into a modular SDK. This requires restructuring the data entities to support multi-tenant usage via clients, custom rules, and detailed reasoning logs.

---

## 1. Cliente (Client) - *NEW ENTITY*
Represents the company or entity contracting the SDK service.

* **id** (String - PK): Unique identifier for the client.
* **nome** (String): Name of the client.
* **access_key** (String): Access key or authentication token used to initialize the SDK.
* **area_atuacao** (String): Market segment or field of operation.

> [!NOTE]
> Currently, the system does not have a `Cliente` entity. This will be the root tenant. The `access_key` will likely replace standard user JWTs for server-to-server or SDK authentication.

## 2. Usuario (User) - *MODIFIED ENTITY*
Indicates the individual person linked to a client who interacts with the platform.

* **id** (String - PK): Unique identifier for the user.
* **nome** (String): Full name of the user.

> [!WARNING]
> **Refactoring Impact**: The current `Usuario` class contains `telefone` and `senha` (password). In an SDK context, user authentication is often handled by the Client's own system. We will need to adapt the `Usuario` entity to drop `senha` and `telefone`, acting mainly as an identifier passed by the Client. A relation to `Cliente` (e.g., `id_cliente`) might also be necessary depending on the final DB schema.

## 3. Pedido (Request / Order) - *REPLACES `Requisicao`*
Logs the prompts or requests sent by the users.

* **id** (String - PK): Unique identifier for the request.
* **id_usuario** (String - FK): Reference to the user who made the request.
* **prompt** (String): The text instruction or question sent.
* **timestamp** (LocalDate): The date when the request was created.

> [!TIP]
> **Refactoring Impact**: The existing `Requisicao` entity will be renamed to `Pedido`. We will rename the `criacao` field to `timestamp`. The existing relationship with `AppSuportado` may need to be re-evaluated or moved into `Personalizacao` depending on SDK boundaries.

## 4. Resposta (Response) - *MODIFIED ENTITY*
Stores the outputs generated by the system for each request.

* **id** (String - PK): Unique identifier for the response.
* **id_requisicao** (String - FK): Reference to the request (`Pedido`) that triggered this response.
* **mensagem** (String): The final text response sent to the user.
* **raciocinio** (String): The reasoning log or internal chain-of-thought/steps taken by the system/AI.
* **timestamp** (LocalDate): The date when the response was generated.

> [!IMPORTANT]
> **Refactoring Impact**: The current `Resposta` entity will gain a new field `raciocinio` to expose the AI's internal reasoning, which is highly valuable in an SDK. The `criacao` field will be renamed to `timestamp`.

## 5. Personalizacao (Customization) - *NEW ENTITY*
Custom rules or settings defined by the client.

* **id** (String - PK): Unique identifier for the customization.
* **regra_personalizada** (String): Description or JSON containing the customization guidelines.

> [!NOTE]
> This entity will likely be linked to a `Cliente` (e.g., `id_cliente` FK) so that every request originating from a specific client's SDK initialization uses these custom rules during processing.

## 6. Componente (Component) - *NEW ENTITY*
Modular elements or metadata attached to a specific response.

* **id** (String - PK): Unique identifier for the component.
* **id_resposta** (String - FK): Reference to the associated response.
* **assinatura** (String): Digital signature or validation of the component.

> [!TIP]
> Components can be used to pass rich UI instructions, function calls, or validation metadata back to the SDK client so it can render natively.

---

## Next Steps for Implementation
1. **Remove API Controllers**: Deprecate REST controllers (`UsuarioController`, `RequisicaoController`, etc.) as the entry points will be SDK interface methods.
2. **Database Migration**: Create Liquibase/Flyway scripts to:
   - Create `Cliente`, `Personalizacao`, and `Componente` tables.
   - Rename `Requisicao` to `Pedido`.
   - Update columns in `Usuario` and `Resposta`.
3. **Refactor Repositories & Services**: Update references from `Requisicao` to `Pedido` and integrate the `Cliente` context into all service calls using the `access_key`.
